# ICR Project Documentation

## Project Overview
This is a single-instance Rails application designed to run for a single company. There is no multi-tenancy support, and company details are managed through a singleton settings model.

### Model Organization
- Employee-related models live under the `Employee::` namespace and use explicit `class_name` in associations (required for the namespace to resolve). Serializers mirror the same namespace.
- Client care-domain models live under the `Client::` namespace (`SupportContact`, `Allergy`, `Diagnosis`, `LifeDetail`, `Enrollment`) with `self.table_name` and explicit `class_name` on `Client` associations. Decent Exposure in nested `Clients::*` controllers must pass `model: Client::...` or it resolves the un-namespaced constant.

## Conventions
### Architecture
- Single-tenant application
- Company settings use singleton pattern
- Front end is Typescript using Yarn, Vite, Inertia.js and React (do *not* use npm or pnpm, this project uses yarn)
- Backend is Ruby on Rails using Inertia
- Audit: paper_trail `versions` is the single audit store. Keep domain state columns that gate behavior on the model (`finalized_at`, `approved_at`, plus standard `created_at`/`updated_at`). Actor and audit-only actions (e.g. payroll export) live only on versions (`whodunnit`, custom `event`) - do not add `*_by` or audit-only `*_at` columns.

### Controller Concerns
- Config used in instance methods (e.g. sortable fields) must use `class_attribute` so each including class gets its own config. Module-level instance variables set in `included` are class ivars and are not visible in instance methods.

### Settings Controllers
- Singleton settings share one update endpoint across multiple Inertia pages. Use `redirect_back_or_to settings_path` so both success and validation errors return to the originating page without losing Inertia error handling.

### Development Guidelines
- No multi-tenancy support
- Changes must be atomic and focused
- Frontend: no default exports; use named exports only (except for the app/frontend/pages directory, those all MUST be default exports). React components use function declarations: `export function ComponentName({ ...props }: Props) { ... }`. Barrel files re-export with `export { X } from "./Y"`. Inertia page modules may export a named `Page` (e.g. `export const Page = withLayout(Inner, "layout")`) for the resolver.
- When checking HTTP response status, use exact status equality (e.g. 201), not range checks.
- TypeScript: strict types, prefer existing types and generics over inline types. Do not use type assertions (as, as unknown as). Do not add explicit return type annotations when TypeScript can infer them; only annotate when intent is genuinely ambiguous. Fix type errors by correcting the types (e.g. union types, generics), not by casting.
- Nested ternaries are disallowed; use `if`/`else` or early returns.
- ASCII punctuation only in all generated or edited text (code, UI copy, docs, commits, locales). Use `'` not curly apostrophes/quotes; use `-` not en-dash (`–`) or em-dash (`—`); use `...` not ellipsis (`…`). Empty/missing display values use `-`, not `—`.

## Feature Documentation
*Document completed features and their core functionality here*

### Dashboard
- Root Inertia page loads `dashboard` props from `Dashboard::StatsSerializer.render(Dashboard::Stats#payload)` so the payload matches `Schema.DashboardStats` from TypesFromSerializers. When `user` is nil, `Dashboard::Stats` uses `Client.none`, `Employee.none`, `Calendar::Event.none`, and `Timesheet.none` instead of calling Pundit, so counts and lists collapse to empty without a separate blank payload path. Nested rows are `Struct` instances; use `Payload#to_h` for plain hashes. `Dashboard::StatsSerializer` and its nested serializers subclass `BaseSerializer` (not `ApplicationSerializer`) so the root DTO is not forced through `identifier`/ActiveRecord-oriented hooks. Counts and lists use `Pundit.policy_scope` for `Client`, `Employee`, `Calendar::Event`, and `Timesheet` so the numbers match what that user could list in those areas. Week hours sum shift lengths (calendar event duration) for scoped employees in the current calendar week. Pending timesheets are unapproved rows for the current pay period when that `PayPeriod` row already exists (GET does not create periods). Recent activity is derived from the newest clients and employees in scope, not from the activity table.

### Client Show
- Client show is URL-tabbed (Overview, Profile, Contacts, Medical, Care and Services, Trainings, Documents, Incidents). Schedule stays a member route. Nested writes live under `/clients/:client_slug/...` and authorize through `ClientPolicy#update?` (show for read). Overview counts and sibling collections come from one `Client.includes_show` load via `Clients::ShowSerializer` so allergy/prescription/support-contact/enrollment/attendant/training/doctor/hospital-visit ids stay lockstep. Medical tab owns preferred hospital, linked doctors (`doctors_clients` notes), allergies, diagnoses (optional `doctor_id`), prescriptions (dosage amount/frequency/`administration_method`), and `Client::HospitalVisit` rows (optional doctor + incident link). CA-aware profile fields and IHSS profile fields live on `clients`; day programs are `Client::Enrollment` rows linked to `Vendor`. Support contacts use Personable (name and Contactable phones/emails/addresses live on Person). Document/image UI uses ActiveStorage `HasDocuments`/`HasImages` list/upload/purge (Phase 2 versioning still open). Client Trainings tab lists `ClientsTraining` join rows (optional link from catalog `Employee::Training`, with `required` for working with that client). Client-schedule requirements gate pairing via `ClientsAttendant` and calendar shifts that include that client.

### Doctors
- Doctors are Personable records with specialty, NPI, practice name, and notes. Show is URL-tabbed (Overview, Clients, Prescriptions, Diagnoses, Hospital Visits) from one `Doctor.includes_show` load. Client linking and prescription/diagnosis/hospital-visit attribution use `DoctorsDropdown` via `GET /api/options/doctors`. Incident reports may reference a doctor; hospital visits may reference an incident. MAR administration logs remain deferred.

### Employee Show

- Employee show is URL-tabbed (Overview, Profile, Contacts, Credentials, Assignments, Trainings, Requirements, Pay, Documents). Schedule and Status stay member routes. Nested writes live under `/employees/:employee_slug/...` and authorize through `EmployeePolicy#update?` (show for read). Overview counts and sibling collections come from one `Employee.includes_show` load via `Employees::ShowSerializer`. Status transitions use AASM events via `PUT .../status` with `employee[event]` (including `begin_employment` for applicant to employed). HR nested models under `Employee::` (`SupportContact`, `Credential`, `Clearance`) need Decent Exposure `model: Employee::...`. Credentials tab covers identifications, credentials, and clearances. Pay tab holds pay-rate history and deep-links to payroll employee review when a current `PayPeriod` row already exists (GET does not create periods). Trainings catalog lives at `/employees/trainings` and is gated by `Employee::Training` job-title grants (`employee_training` in the permissions matrix); assigning/editing dates on an employee uses employee update, while setting `completed_at` requires the `complete` grant on `Employee::Training` (seeded for Facilitator; Director via grant-all). Requirement fulfillment is computed live by `Requirement::FulfillmentForEmployee` from the same show load and passed as `requirement_fulfillments` (Overview unmet count + Requirements tab).

### Requirements
- Admin CRUD lives under Settings > Company > Requirements (`/settings/requirements`, types at `/settings/requirement_types`). A requirement belongs to a `Requirement::Type`, optional polymorphic scope (`Employee::JobTitle`, `Client`, or company-wide when blank), an `enforcement` (`advisory`, `employment`, `client_schedule`), and `Requirement::Item` rows that are either an `Employee::Training` fulfillable or a `credential_type` matching `Employee::Credential` (XOR). Satisfaction is AND across items: training items need `EmployeesTraining.completed_at`; credential items need a non-expired credential of that type. `Requirement::FulfillmentForEmployee` evaluates applicable requirements live (no persisted fulfillment rows). `Requirement::EmploymentGate` blocks `begin_employment` / `accept_offer` (and `Offers::Accept` hires). `Requirement::ClientScheduleGate` blocks `Calendar::Event` saves that pair a shift employee with a client participant, and `ClientsAttendant` create/client changes. Permissions catalog key is `requirement` (`Requirement::Requirement`); type CRUD reuses those grants via `Requirement::TypePolicy`. Dev seeds include Attendant DL employment, first-client protocol training (`client_schedule`), and advisory First Aid.

### Permission System
- Single stack: Devise auth, Rolify roles, Pundit policies. Job Titles are the admin-facing permission surface (Settings > Job Titles matrix).
- Resource x action grants live as Rolify roles on `Employee::JobTitle` (e.g. `job_title.has_role?(:index, Client)`). User-level `:admin` bypasses all checks.
- Relationship limits stay in Pundit scopes/policies: attendants via `ClientsAttendant`, managers via `ClientsManager` / `Employee::EmployeesManager`, self via own employee/timesheet/shift.
- Shared Inertia `permissions` hash is built from Pundit policy methods and cached per user; job title role changes invalidate those cache keys.
- Job-title "Grant all listed actions" checkbox expands to every catalogued resource action; it is not the same as user `:admin`.
- Catalog resources used as Rolify targets need `resourcify` on the model (e.g. `ClientsManager`); without it, `SyncPermissions` fails with "Resource type Doesn't exist".
- Title-scoped gates: add the action to `PermissionsCatalog` (CRUD or `EXTRA_ACTIONS`), grant it in `db/seeds/02_required_permissions.rb`, and check via `standard_auth` / `job_title_allows?`. Do not hardcode job title names in policies.

### Caseloads
- Org-wide facilitator caseloads are `ClientsManager` rows (`manager` = facilitator employee). `/caseloads` is gated on `permissions.clients_managers` (`ClientsManagerPolicy`). Nested employee/client manager tabs stay the per-record editors.
- Facilitator roster query: join `Employee.actively_employed` through `Employee#active_employees_job_title` (uses `1.second.from_now`). Do not use `Employee::JobTitle#active_employees` for same-day assignments - that association compares `starts_at` to `Date.current` (midnight) and drops rows that started later the same day.

### Payroll Settings
- Period types: weekly, bi-weekly, semi-monthly, monthly. Weekly/bi-weekly use a start weekday; monthly uses a configurable start date (including last day of month). Semi-monthly is fixed: 1st-15th and 16th-last.
- Payroll due date: user-configurable setting that defines when the approval window closes for each period; supports multiple rule types (e.g. days after period end, day of week after period end, day of month). See payroll workflow redesign plan.
- Overtime: configurable weekly/daily thresholds; exemption rules by shift category, time range, duration.
- Pay rates: historical records with effective dates; hourly and salary; currency.

## Technical Decisions
### Authentication & Authorization
- Devise, Pundit, Rolify. Job title Rolify roles drive resource/action grants; Pundit encodes relationship-scoped access. No separate Permission::Group system.

### Document Management
- Active Storage; versioning for important documents; Pundit for access.

### Calendar System
- Multiple view strategies; timezones must be handled correctly; recurring events follow RFC 5545 (iCalendar).
- Recurring events: one master `Calendar::Event` plus `Calendar::RecurringPattern` definition rows (daily/weekly/monthly/yearly, interval, ends never/on date/after N). Schedule APIs load masters via `for_schedule_range`, then `Calendar::RenderSchedule` expands occurrences with `Calendar::Recurring::ExpandOccurrences` (cancels/reschedules applied) and sends occurrence rows over the wire (`master_id`, `occurrence_starts_at`, `is_recurring`, display `starts_at`/`ends_at`). The calendar frontend maps those rows; it does not expand recurrence in JS. Create and edit share one EventForm with Repeat fields (hydrated from series patterns on edit). On save of a recurring edit, choose all / this-and-future / just-this (`edit_scope` all|future|one). All shifts the master by `(form_starts_at - occurrence_starts_at)` so date moves apply to the whole series; future truncates and continues; just-this detaches. All/future can replace pattern rows.
- One display-setting drives both month and time-grid views (month strategies vs overlap for day/week), so per-strategy behavior can be added without changing the public API.
- Gotcha: The popover closes on click-outside. Date/time pickers or other inputs inside the popover must not use a portal, or the popover will close when the user selects a value.
- Client schedule: Events come from React Query; mutations must invalidate the schedule query so the calendar refetches. If invalidation is skipped, the UI can show stale or duplicate events.
- Client schedule uniqueness: Participantable's calendar_events is has_many through event_participants; the join can return the same event multiple times. The association uses a distinct scope so the API returns each event once.
- Gotcha: If a Calendar::Event relation uses joins and also includes employee job_title (via Employee's active job title scope), Postgres can raise "column reference starts_at is ambiguous". Avoid by filtering events via a subquery of ids, then applying includes on the outer relation (no joins on the outer query).

### Timesheet System
- Payroll is a time-approval and period-integrity workflow (approve timesheets, finalize/lock the period). A vendor-neutral hours export is available after finalize. EVV is deferred; keep shift and calendar_event identity intact as the future attachment point.
- Two view families per period: **clients-first** (`/payroll/periods/:id/clients` and client drill-down) for facilitator caseload review and Director oversight; **employee-combined** (`/payroll/periods/:id` plus employee review) for Director final approve, finalize, and export. Facilitators without Timesheet `index` are redirected from the employee-combined period show to the clients board.
- Facilitator review is shift-level (`shifts.facilitator_approved_at`), authorized when every Client on the event is on the facilitator's active `ClientsManager` caseload. Director final approval is timesheet-level (`timesheets.approved_at`). Directors may final-approve with unreviewed shifts; the UI warns with the gap list. Finalize and export never wait on facilitator stamps.
- Payroll IA: `/payroll` is an attention home (counts + CTA into the current period); employee review is the timecard drill-down for the combined sheet.
- Employee payroll review: per-employee view for a pay period; authorization follows timesheet show; Director final approve uses `final_approve?` (Timesheet `index`).
- PayPeriod: one per (starts_at, ends_at); no overlapping periods; derived from settings. Use PayPeriod.for_period_dates(start_date, end_date) to resolve a period: it reuses a period that starts on the same calendar day (snapping end to the canonical range; timezone-safe), or creates one and shrinks any predecessor that overlapped into that range. Shrinking reattaches out-of-range shifts via PayPeriod.attach_shift!.
- Timesheet: pre-submittal; tracks Director approval; belongs to PayPeriod and Employee; has many Shifts.
- Shift create: PayPeriod.attach_shift! finds or creates the pay period that contains the shift date and attaches a timesheet. Pay periods appear because shifts are scheduled into them.
- PayPeriod create/sync: sync_shifts! finds shifts via `Calendar::Event.for_schedule_range` (so recurring masters that expand into the period count). Non-recurring overlapping shifts are attached to this period's timesheets; recurring masters keep their original timesheet, and the period still gets an employee timesheet row so they appear in payroll.
- Payroll index hours: Payroll::EmployeePeriodHours computes per-employee regular_hours, ot_hours, ihss_hours, and company_hours for a pay period. Uses Setting overtime_weekly_hours and overtime_daily_hours; splits work intervals by day (including overnight); applies active OvertimeExemption rules to exclude exempt intervals from OT; weekly OT and daily OT are summed. IHSS classification runs first via Payroll::IhssHourClassifier (shift flag or period assignments). When Setting.ihss_co_employer is false, only company hours feed OT math; when true, all hours feed OT. The calculator reads intervals via a collector interface (default: scheduled shifts), so payroll can later swap in a clock-in/out collector without changing overtime math or UI contracts.
- Recurring shifts in payroll: same Ruby expand-on-read path as schedule APIs (`Calendar::Recurring::ExpandOccurrences`). `Payroll::WorkIntervalCollectors::ScheduledShifts` expands masters into period occurrences for hours; it does not require the master `timesheet_id` to point at the current period.
- IHSS settings (Settings > Payroll > IHSS): `ihss_co_employer` and `ihss_assignment_mode` (`shift` | `period`). Shift mode toggles `shifts.ihss` in payroll review. Period mode stores `Payroll::IhssPeriodAssignment` rows (pay period + employee + client + hours) and consumes those hours chronologically against matching client shifts. Client payroll boards show IHSS hours used in the period next to `clients.ihss_authorized_hours`.
- Payroll approval UI: Director Approve / Unapprove / bulk approve stay available until the period is finalized (`can_approve = !finalized?` for index holders). The payroll due date and `approval_window_open` are deadline / urgency signals only; they must never hard-block approval. Hard-close language in the older payroll redesign plan is superseded by this rule.
- Approval reminder emails: `Payroll::SendApprovalReminders` (daily GoodJob cron) emails admins and Timesheet approvers for closed, unfinalized periods with pending Director approvals. Facilitators (update without index) get a count of pending caseload shifts. Org-wide enable/disable lives under Settings > Notifications (`Setting.notifications_payroll_approval_reminders`).
- Manual shift entry on employee payroll review creates a `Calendar::Event` + nested `Shift` via `POST /api/calendar_events` (same path as schedule); `PayPeriod.attach_shift!` wires the timesheet. Create into a finalized period is rejected. Attaching a shift or changing event times/participants clears timesheet `approved_at` and shift `facilitator_approved_at`. Review rows show `last_editor` from the latest paper_trail time update on the calendar event (initials avatar + tooltip).

#### Type System
- Strict TypeScript; prefer existing types and generics.
- **NEVER use type assertions (typecasting).** No `as`, no `as unknown as`, no `as any`. If something does not type-check, fix the types (e.g. add a union type, widen a generic, export a type the API accepts). Casting is a project rule violation.
- **NEVER add explicit return types** on functions when the return type can be inferred. Let TypeScript infer. Only add a return type when it is required for a public API or when inference is genuinely wrong/ambiguous.
- Do not use `any` or `unknown` as escape hatches; do not add unnecessary type annotations on variables when the literal or expression already satisfies the expected type.
- These TypeScript rules are non-negotiable. When in doubt, try without the cast or annotation first; the code often already type-checks.
- Ruby constants can be exported to TS via rails types:generate; add a subtask in types.rake so it stays in sync.
- moduleResolution "bundler" is required for subpath exports (e.g. tiptap menus).

#### Internationalization (i18n)
- react-i18next; locales from Rails (i18n-js). Model-specific frontend strings in config/locales/[model]/frontend.en.yml; rest in frontend.en.yml. Keys: views.[feature].[page].[key]. Controller notices use shared templates under templates.controllers.notices with %{model}; CRUD notices (created/updated/destroyed/status_updated) use these.
- RSpec (`spec/i18n_spec.rb`) asserts there are no missing keys reported by i18n-tasks for references under `app/` (including TSX). Other i18n-tasks reports (unused, normalize, interpolation) are optional; run `bundle exec i18n-tasks` when needed.
- Devise Inertia pages use `config/locales/devise/frontend.en.yml` under `views.devise` (shared copy such as `views.devise.shared.email`, per-flow keys such as `views.devise.confirmations.new.title`).

#### Testing
- Unit: Vitest + RTL; E2E: Playwright (no mocks). Tests mirror app/frontend under app/frontend/tests.
- Gotcha: For assertions on translated strings, run validation and assertions inside I18n.with_locale(:en) so the expected message is stable.
- Gotcha: Forms must use remember={ false } or the form library can persist state across unmount/remount and tests see stale values.
- Gotcha: For form-context tests, use Form from use-inertia-form (not the app Form wrapper). For Mantine, wrap with MantineProvider, stub matchMedia in beforeEach, and wrap Grid.Col in Grid.
- Do not test literal constants from the source; test behavior, branches, and contracts.
- Prefer smoke-level checks for presentational layout (e.g. main content renders, interactive regions exist) over asserting element order, separators, or exact hrefs unless that order is a behavioral contract.

#### Serializers
- Smoke spec discovers serializers, infers model from name, renders each. Slug-identified models need persisted records so the smoke spec creates them. Gotcha: Identification uses the id_type column; serializers must use :id_type, not :type.

#### Lib coverage
- spec/lib covers lib code; generator specs live under spec/lib/generators. Gotcha: In specs that register at-exit blocks with doubles, stub the class's at_exit so real at-exit is not registered.

#### Performance
- Code splitting, lazy loading, memoization, minimal global state.

#### TipTap Integration
- TipTap v3.14.0; Mantine integration via @mantine/tiptap. Gotcha: Menu components (BubbleMenu, FloatingMenu) must be imported from the /menus subpath, not the main package.

## Payroll Periods

### Semi-Monthly
- With "last day of month" setting: first period 1st-14th, second 15th-last day. Otherwise two configurable dates; each period ends the day before the next starts.

### Bi-Weekly
- Fixed reference date for boundaries; 14-day periods; configurable start day of week.

### Weekly
- Configurable start day of week; 7-day periods.

### Monthly
- Configurable start date or "last day of month." When last day: period is last day of prior month through second-to-last day of current month. Otherwise ends day before next period's start.
